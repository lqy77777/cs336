## 1. 脚本结构：该不该写 `main()`？

**该写。** 而且建议拆成三层：

### 1.1 三个层次

| 层 | 职责 | 为什么单独拆 |
|---|---|---|
| **参数解析函数** | 定义所有命令行参数，返回配置对象 | 可以被测试；扫参数时可以绕过命令行直接构造配置 |
| **`main(args)`** | 完整的训练流程 | 可以被其他脚本 import 后直接调用 |
| **`if __name__ == "__main__":` 守卫** | 只在直接运行时执行 | 见下文三条理由 |

再往下可以按需拆出「构造模型」「跑一次验证」「记录日志」等辅助函数。

### 1.2 为什么必须有 `if __name__ == "__main__":` 守卫

**理由一：可导入而无副作用。**
没有守卫的话，任何 `import` 这个模块的行为都会**立刻开始训练**。你想在 notebook 里复用其中一个函数？训练就跑起来了。

**理由二：多进程的硬性要求。**
macOS 和 Windows 上 Python 的多进程默认用 `spawn` 方式——子进程会**重新 import 主模块**。没有守卫的话，每个子进程都会再启动一次完整训练，然后它们各自再 fork 子进程……瞬间炸掉。

你现在还没用 `DataLoader` 的多 worker，但 BPE 训练用过多进程，将来做数据预处理也会用到。**这是一个只在出事时才发现、且症状极其诡异的坑。**

**理由三：这是 Python 社区的通用约定。**
别人看你的代码，第一眼找的就是这个入口。

### 1.3 为什么 `main` 要接受参数而不是自己解析

把「解析命令行」和「执行训练」分开，你才能：

- **做超参数扫描**：写一个外层脚本，循环构造不同的配置，直接调 `main(config)`——不必反复 subprocess 启动进程
- **写集成测试**：用一个极小的配置调 `main`，验证整个流程能跑通
- **从配置文件启动**：以后想换成 YAML 配置，只要改解析层

后面的 `learning_rate` 实验（2 B200 小时）和 `batch_size_experiment` 都要跑很多次，这个设计能省不少事。

### 1.4 文件放哪

建议单独一个文件，例如 `cs336_basics/train.py` 或项目根目录的 `scripts/train.py`。

**不要**塞进 `training.py`——那里是被测试 import 的库代码，不该有可执行脚本的入口。

## 3. 五个区块

### 区块 1：解析参数

除了 `argparse` 的常规用法，两个建议：

- **把配置完整打印一遍**（或存成 JSON 放进 checkpoint 目录）。做几十次实验之后，「这个结果是哪组参数跑出来的」会变成一个真实的问题
- **做参数合法性断言**：`d_model % num_heads == 0`、`warmup_iters < cosine_cycle_iters`、`batch_size > 0`。早失败比晚失败便宜

### 区块 2：准备阶段（按顺序）

**① 设随机种子**

torch 和 numpy **都要设**。你的 `data_loader` 用的是 numpy 的全局随机数，模型初始化用的是 torch 的。只设一个的话结果仍然不可复现。

**② 解析 device**

Mac 上是 `'mps'`。建议写一个自动探测的逻辑（有 cuda 用 cuda，有 mps 用 mps，否则 cpu），同时允许命令行覆盖。

**③ 加载数据**

用 `np.load(path, mmap_mode='r')` 或 `np.memmap`。

⚠️ **两个必查项**：
- **dtype 必须和保存时一致**。不一致不会报错，只会读出垃圾
- **立刻做值域检查**：`max() < vocab_size` 且 `min() >= 0`。这一步能在训练开始前就抓住 dtype 错误

> 为什么值域检查能抓 dtype 错误：如果数据存的是 `uint16` 而你按 `int32` 读，每两个 token 会被拼成一个巨大的整数，`max()` 会远超 vocab size，一眼就看出来。

**④ 构造模型并搬到 device**

**⑤ 构造优化器**，传入 `model.parameters()`

**⑥ 可选：恢复 checkpoint**

如果命令行给了 `resume_from`，调 `load_checkpoint` 拿回起始 iteration。这决定了主循环的起点——**从 0 开始还是从恢复的那一步开始**。

⚠️ 恢复时模型必须用**相同的配置**构造。你的 RoPE buffer 用了 `persistent=False`，它不在 checkpoint 里，是构造时重新算的——配置不一致的话表算错了，而 `load_state_dict` 完全察觉不到。

### 区块 3：主循环

每一步依次做七件事：

1. **算学习率**——用当前 iteration 调 `cosine_learning_rate`，把结果**写进 optimizer 每个参数组的 `'lr'`**
2. **采一个训练 batch**——调 `data_loader`
3. **前向 + 算 loss**——模型输出 logits，交给 `cross_entropy` 得到标量
4. **清梯度 + 反向传播**
5. **梯度裁剪**
6. **优化器更新**
7. **周期性任务**——验证 / 日志 / checkpoint

### 区块 4：周期性任务

**验证 loss**

- 必须包在 `torch.no_grad()` 里，否则显存翻好几倍
- **取多个 batch 求平均**，单个 batch 的噪声太大，曲线会没法看
- ⚠️ **固定验证数据**——用固定 seed 或者预先采好一组固定的验证 batch。否则每次验证喂的数据都不同，曲线的抖动来自采样而不是模型，你无法判断模型到底有没有变好

**日志**

至少输出：iteration、train loss、当前 lr、累计 wall-clock 时间。

**checkpoint**

- 建议**定期覆盖同一个文件**（用于崩溃恢复）**+ 关键节点另存**（用于事后分析）
- 只留最新的会让你在训练崩掉时无法回退到更早的健康状态；每次都另存会塞满磁盘

### 区块 5：收尾

训练结束时存最后一个 checkpoint，打印总耗时和最终 loss。

## 4. 三个顺序约束及其原因

这三处放错都会导致**训练能跑但结果错**，是最难 debug 的一类问题。

### 约束 1：清梯度必须在反向传播之前

PyTorch 的梯度是**累加**的（`p.grad += 新梯度`，不是覆盖）。不清零的话，第 $t$ 步用的是前 $t$ 步梯度的总和，等效学习率被放大了 $t$ 倍。

> 顺带：这个累加语义正是「梯度累积」技巧能成立的原因——显存装不下大 batch 时，可以跑 4 个小 batch、连续反向 4 次、再更新一次。

### 约束 2：梯度裁剪必须夹在反向传播和优化器更新之间

放在反向传播之前——没有梯度可裁。
放在优化器更新之后——参数已经被巨大的梯度推飞了。

### 约束 3：学习率必须写进 `param_groups`，且在更新之前

调度器改的是 `group['lr']`，优化器的 `step` 读的也必须是 `group['lr']`。

**如果你的 AdamW 里读的是 `self.lr` 之类的实例属性，调度器会完全失效——而且不报错。** 训练照跑，loss 照降，只是 warmup 和衰减根本没生效。

这就是为什么「超参数必须放在 `param_groups` 里」是一条硬性契约。

## 5. 验收：没有自动测试，怎么知道对了

按顺序做，**前面的不过就别做后面的**。

### ① 初始 loss ≈ $\ln(\text{vocab\_size})$ ⭐ 最便宜也最灵敏

随机初始化的模型对下一个 token 的预测应该接近**均匀分布**，此时交叉熵是

$$-\log \frac{1}{V} = \ln V$$

vocab = 10000 时，初始 loss 应该在 **9.21** 附近。

| 观察到的现象 | 可能原因 |
|---|---|
| 明显更高（如 15+） | 初始化方差太大；或 logits 尺度失控 |
| 明显更低（如 2） | 数据泄漏（输入里已包含答案）；或 loss 算错 |
| `nan` / `inf` | 数值稳定性问题；检查 cross_entropy 的减最大值是否生效 |
| 恰好 ≈ 9.21 | ✅ 模型、数据、loss 三者基本都对 |

这一条**花 10 秒钟**，能排除掉一大半的低级错误。

### ② 在极小数据上过拟合 ⭐ 最强的 sanity check

拿几十到几百个 token 反复训练（同一批数据循环喂），关掉 weight decay。**loss 必须能降到接近 0。**

- 能降到 0 → 模型结构、前向、反向、优化器**全链路正常**。剩下的问题都是超参数问题
- 降不下去 → 实现有 bug，别浪费时间调学习率

这一步的价值在于**把「实现错误」和「超参数不好」彻底分开**。没有它，你会在两者之间反复横跳。

### ③ 中断恢复曲线重合

跑 20 步 vs 跑 10 步 → 存 → 重启 → 再跑 10 步。两条 loss 曲线应当**完全重合**。

⚠️ 做这个测试时要**固定数据采样的随机性**，否则两条路线喂的 batch 不同，曲线本来就不会重合。

> 这也揭示了一个真实问题：严格来说，**数据加载器的随机状态也属于「训练进度」**。本作业不要求存它，但生产系统里这是必须处理的。

### ④ 学习率曲线符合预期

把每步的 lr 记录下来画图，应该看到：**线性上升（warmup）→ 余弦下降 → 平台**。

**如果它是一条水平线**，说明调度器没生效——十有八九是约束 3 被违反了。

## 6. 建议额外记录的指标

handout 没要求，但对后面几十小时的实验帮助极大：

| 记录什么 | 为什么 |
|---|---|
| **梯度范数（裁剪前）** | 训练不稳定时，梯度范数的尖峰**比 loss 更早**发出预警。看到范数持续攀升就该警觉了 |
| **实际被裁剪的比例** | 如果每一步都在裁剪，说明 $M$ 设得太小，等于给学习率加了个隐形的上限 |
| **wall-clock 时间 / tokens per second** | 后面的实验按 B200 小时计费，需要知道吞吐才能估算 |
| **train / val loss 分开** | 判断过拟合的唯一方式 |
| **完整超参数配置** | 三周后你不会记得某次实验用了什么参数 |

## 8. 常见坑清单

1. **忘记 `model.train()` / `model.eval()`** —— 本作业的模型没有 Dropout 和 BatchNorm，暂时无影响，但要养成习惯
2. **验证时忘记 `torch.no_grad()`** —— 显存翻几倍，长序列直接 OOM
3. **验证数据每次都重新随机采** —— 曲线抖动来自采样噪声，无法解读
4. **数据没用 memmap** —— 大数据集直接 OOM
5. **memmap 的 dtype 写错** —— 静默读出垃圾，模型永远学不会
6. **模型和数据不在同一个 device** —— 会响亮报错，好排查
7. **学习率调度器改了 `group['lr']` 但优化器没读它** —— 静默失效
8. **没有 `if __name__ == "__main__":` 守卫** —— 多进程场景下无限递归启动
9. **checkpoint 只存不清理** —— 磁盘塞满，训练在深夜静静死掉
10. **没记录超参数** —— 实验做完了，但不知道是哪组参数
