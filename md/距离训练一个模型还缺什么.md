## 0. 一句话结论

**零件全齐了,管道一根没有。**

47 个测试全过(1 个 xfail 是预期的),说明单个组件的数学都对。但从「一个 `.txt` 原始语料」到「一个训练好的 checkpoint」这条链路上,**没有任何一环是通的**——缺的不是算法,是把零件串起来的胶水,以及零件之外的数据准备。

## 2. 缺口 A:数据管道(最大的一块,完全空白)

完整链路应该是:

```
原始 .txt  →  训练 BPE  →  vocab/merges 落盘  →  编码全量语料  →  token id 数组落盘  →  memmap 读取
   A1           已有          ✗ A2                  ✗ A3              ✗ A3            ✗ A4
```

### ☐ A1. 数据集还没下载

`data/` 目录不存在。命令在 [../README.md](../README.md) 的 "Download data" 一节里已经给好了(TinyStoriesV2 的 train/valid,加 OWT 的 sample)。

下载完先做两件事:`ls -lh data/` 看清文件到底多大,以及 `head -c 2000` 看一眼真实文本长什么样。后面估算「编码要多久」「token 总数多少」都要用到这两个数。

### ☐ A2. vocab / merges 没有序列化 —— `Tokenizer.from_files` 还是 `pass`

见 [bpe.py:163-170](../cs336_basics/bpe.py#L163-L170)。

这是**第一个必须自己做的设计决策**,而且比它看起来的要棘手:

- `train_bpe` 返回的 `vocab: dict[int, bytes]` 和 `merges: list[tuple[bytes, bytes]]` 都活在内存里,进程一结束就没了。而 BPE 训练在 TinyStories 全量上是**小时级**的开销——你绝对不想每次训练模型都重跑一遍。
- **`bytes` 不能直接进 JSON。** 这是核心难点。你需要选一种编码方式,并且保证「存下去再读回来」和原始 `bytes` **逐字节相等**。想清楚:任意 0–255 的字节序列(包括非法 UTF-8 的那些)怎么无损地表示成文本?
- 可以参考的现成格式:`tests/fixtures/gpt2_vocab.json` 和 `gpt2_merges.txt` 就是 GPT-2 的存法,打开看一眼它是怎么处理不可打印字节的。`tests/adapters.py` 里 `get_tokenizer_from_vocab_merges_path` 附近也有相关线索。

**验收标准**(自己加断言,没有现成测试):存盘再读回来的 tokenizer,对同一段文本 `encode` 出来的 id 序列必须和原 tokenizer **完全一致**;`vocab` 的每一个 `bytes` 值都要 round-trip 相等。

### ☐ A3. 没有「把整个语料编码成 token id 数组」的脚本

这是一个独立的一次性脚本(不是 `train.py` 的一部分)。要点:

- **必须用 `encode_iterable`,不能用 `encode`。** 上面那条 xfail 就是原因:整个文件读成一个 str 再 encode 会爆内存。
- **dtype 的选择**:vocab size 10000 → 最大 id 9999 → `uint16`(上限 65535)够用,比 `int32` 省一半磁盘和一半 page cache。但**必须加断言**验证 `max_id < 65536`,否则将来把 vocab 调到 100k 时会静默溢出——这种 bug 训练能跑,loss 就是不降。
- **train 和 valid 分开编码**,用同一个 tokenizer。
- **把 token 总数打印并记下来**。缺口 B 里算 step 数要用它:讲义要求 `batch_size × steps × context_length ≈ 327,680,000`,你得知道自己的语料够不够跑这么多、要过几个 epoch。
- 建议**先在 valid 集上跑通全链路**(它小得多),确认格式和 round-trip 都对,再去动 train 集。

### ☐ A4. 训练时怎么把它读进来

你的 [tool.py:16](../cs336_basics/tool.py#L16) `data_loader` 直接接受 `NDArray`,而 `np.memmap` / `np.load(..., mmap_mode='r')` 返回的对象支持一样的 fancy indexing,所以**可以无缝喂进去**,只有被索引到的页会进内存。这块设计是对的。

需要你自己确认的:读回来时 **dtype 和写出去时是否一致**。裸 `.npy` 有 header 记录 dtype(用 `np.load(mmap_mode='r')` 更安全),裸 `.bin` 没有(用 `np.memmap` 就必须手填,填错不报错只出垃圾)。这个选择在 A3 就要定下来。

### ☐ B-特别项:验证集评估函数还不存在

这是**除了 `train.py` 本身之外,唯一还需要新写的函数**。`tool.py` 里没有它,`optimizer.py` 里也没有。它不只是「跑一次 forward」:

- 必须在 `torch.no_grad()`(或 `inference_mode`)下,否则白占激活显存
- 要在**多个 batch 上平均**,单个 batch 的 loss 噪声太大,画出来的曲线会毛刺得没法比较不同 run
- 评估用的 batch 该不该固定?想一想:如果每次评估都随机采样,你看到的 val loss 波动里有多少是模型变了、多少是数据变了?这直接影响你能不能判断「lr=3e-4 比 1e-3 好」
- 讲义 §4.1 式 (18) 要求报告 **perplexity**,它和你的 `cross_entropy` 输出是什么关系?
- 评估完记得把模型切回 train 模式(你的模型现在没有 dropout/BN,所以暂时无害——但想清楚为什么无害)

### 讲义给定的超参默认值(§7.2.1,p.39)

这些是**指定值,不用自己调**,直接作为 argparse 的 default:

| 超参 | 值 |
|---|---|
| `vocab_size` | 10000 |
| `context_length` | 256 |
| `d_model` | 512 |
| `d_ff` | 1344(≈ 8/3 × 512,且是 64 的倍数) |
| `num_layers` | 4 |
| `num_heads` | 16 |
| `rope_theta` | 10000 |
| 总处理 token 数 | **327,680,000** = `batch_size × steps × context_length` |

### 低资源档(CPU / MPS,讲义 p.40)

如果不用 GPU,讲义允许:总 token 数降到 **40,000,000**,目标 val loss 从 1.45 放宽到 **2.00**。参考配置 `32 × 5000 × 256 = 40,960,000`,官方在 M4 Max 上 cpu 1h22m / mps 36min,step 5000 时 val loss 1.80。

`torch.compile` 可以加速:cpu 上直接 `torch.compile(model)`;mps 上要用 `backend="aot_eager"`(Inductor 在 mps 上到 torch 2.9 还不支持)。

## 4. 缺口 C:解码 / 生成(§6,3 分)

`transformer.py` 里有 `softmax`,但没有任何采样逻辑。四个要求:

- 给定 prompt 续写,直到生成 `<|endoftext|>` 或达到用户指定的最大 token 数
- **temperature scaling**(式 23):softmax 前把 logits 除以 $\tau$
- **top-p / nucleus sampling**(式 24):按概率排序,取累积概率刚好 ≥ p 的最小集合,在这个集合内重新归一化后采样
- 从 logits 矩阵里取**最后一个位置**的那一行(式 22),这是最容易写错的地方

**为什么训练阶段也需要它**:val loss = 1.45 是个抽象数字,你需要看到真实生成文本才知道模型到底学没学会。讲义 §7.2 给了 TinyStories 的参考输出(以及低资源档的参考输出)让你对比自己的模型好到什么程度。

## 5. 缺口 D:实验基础设施(§7.1 明确要求交付)

讲义原文:*"Logging infrastructure code for your experiments **and an experiment log** (a document of all the things you tried)"* —— 这是**打分的 deliverable**,不是可选项。

- **日志**:print 到 console 不够,你需要能**画出 loss 曲线**并且**把多条曲线叠在一张图上比较**。wandb 最省事,或者自己写 csv/jsonl + 画图脚本。
- **实验记录文档**:每次 run 的超参、结果、你当时的判断。
- **run 目录约定**:每个 run 一个目录,里面放 config(把解析出的参数完整 dump 一份)、loss 曲线数据、checkpoint。这一条在 §7 会救你的命——那一节要交至少 **6 组学习曲线对比**:
  - `learning_rate`(3 分):lr sweep,**且必须包含至少一条发散的曲线**;要达到 val loss ≤ 1.45
  - `batch_size_experiment`(1 分):batch 从 1 扫到显存上限
  - `layer_norm_ablation`(1 分):去掉 RMSNorm
  - `pre_norm_ablation`(1 分):改成 post-norm
  - `no_pos_emb`(1 分):去掉 RoPE(NoPE)
  - `swiglu_ablation`(1 分):SwiGLU vs 纯 SiLU FFN(`d_ff = 4 × d_model` 以配平参数量)
  - `main_experiment`(2 分):换到 OpenWebText

  这些 ablation 都要求**改架构再训练**。现在就想清楚:是加 flag 让 `transformer_block` 支持 `--no-rmsnorm` / `--post-norm` / `--no-rope` / `--ffn-type`,还是每次改代码?前者会让 §7 轻松很多,也让你的实验记录和代码对得上。

## 6. 现有代码在真实训练下会踩的坑

这些**不是缺功能**,是测试覆盖不到、但一上真实训练就会咬人的地方。全部以问题形式给出,自己验证:

### ① 设备处理:`self.device` 与 `.to()` 的不一致 ⭐ 最可能第一天就撞上

见 [transformer.py:140](../cs336_basics/transformer.py#L140)、[transformer.py:166](../cs336_basics/transformer.py#L166)、[transformer.py:169](../cs336_basics/transformer.py#L169)。

`self.device` 存的是**构造时传入的值**。如果你在 `train.py` 里习惯性地写 `model = transformer_lm(...).to('cuda')` 而不是构造时传 `device='cuda'`,那 `self.device` 仍然是 `None`。

问一问自己:
- `nn.Parameter` 会跟着 `.to()` 走,那 `torch.arange(seq_len, device=self.device)` 和 `torch.tril(torch.ones(..., device=self.device))` 这两个**临时张量**会吗?
- 报错会长什么样?(提示:`Expected all tensors to be on the same device`)
- 有没有办法让这些临时张量**永远**跟随参数所在的设备,而不依赖构造参数?(两个方向:从输入 `x.device` 拿,或者做成 buffer——你在 RoPE 里已经用过 `register_buffer` 了)

### ② causal mask 每步每层重建

见 [transformer.py:169](../cs336_basics/transformer.py#L169)。

每次 forward 都 `torch.tril(torch.ones(256, 256))`。4 层 × 5000 步 = 2 万次分配加 2 万次 `tril`。

RoPE 的 cos/sin 表你已经想到用 `register_buffer(persistent=False)` 缓存了——**mask 为什么不行?** 它依赖的量和 RoPE 表依赖的量,性质上有什么区别吗?(`max_seq_len` 你已经传进来了)

### ③ AdamW 的 `m` / `v` 是 out-of-place 更新

见 [optimizer.py:63-64](../cs336_basics/optimizer.py#L63-L64)。

你在 65 行写了注释「这里必须要原地运算,否则会增加内存」,而 66–67 行的 `p.data -=` 确实是原地的。但 63–64 行的 `m = beta_1 * m + (1-beta_1) * grad` **不是**。

算一算:这两行各分配几个临时张量?17M 参数、float32,一步下来多出多少显存峰值?(它不是泄漏,`state['m'] = m` 之后旧的会被回收——但峰值和分配器压力是实打实的)顺带想想 `torch._foreach_*` 或 `add_` / `mul_` 系列能不能用上。

### ④ `gradient_clipping` 每步强制一次 GPU→CPU 同步

见 [optimizer.py:100](../cs336_basics/optimizer.py#L100)。

`norm = sqrt(norm)` 这里的 `sqrt` 是 `math.sqrt`,而 `norm` 此时是个 0 维 tensor。`math.sqrt` 作用在 tensor 上会隐式调用 `.item()` ——这会**阻塞等待 GPU 算完**。

问:每步一次同步,对你的训练吞吐影响有多大?能不能全程留在 tensor 域里(`torch.sqrt`、`torch.where`),让 `norm <= M` 的判断也不出 GPU?怎么用 profiler 确认这一行到底值不值得优化?

### ⑤ `load_checkpoint` 没有 `map_location`

见 [tool.py:46](../cs336_basics/tool.py#L46)。

`torch.load(src)` 会按**存的时候**的设备来放张量。问:
- 在 GPU 机器上存的 checkpoint,拿到只有 CPU 的机器上 load,会怎样?
- 反过来呢?
- 另外 torch 2.6 起 `torch.load` 的 `weights_only` 默认值变成了 `True`。你存的 dict 里有 `model` / `opt` 两个 state_dict 加一个 int——受影响吗?先在自己的 torch 版本上试一次,别等训练跑了三小时才发现恢复不了。

### ⑥ checkpoint 里没有 RNG 状态

见 [tool.py:38](../cs336_basics/tool.py#L38),存的是 `{'model', 'opt', 'iteration'}`。

你自己在 [Section5_训练循环任务清单.md](Section5_训练循环任务清单.md) 的验收清单里写了这条**黄金标准**:「杀掉进程后能接着跑,**且 loss 曲线在接续处平滑**」。

那么:
- `data_loader` 用 `np.random.randint` 采样。恢复之后,拿到的 batch 序列和「没中断的那个 run」一样吗?
- 如果不一样,接续处的 loss 会不会有一个小台阶?你怎么区分「台阶是 RNG 造成的」还是「优化器状态没恢复对」?
- 想让它完全可复现,还需要存什么?(numpy 的、torch 的、CUDA 的,各有一份)

### ⑦ `data_loader` 的边界条件

见 [tool.py:24](../cs336_basics/tool.py#L24):`np.random.randint(0, n-m, size=B)`。

拿笔算一遍,不要凭感觉:
- `n = 10, m = 9` 时,`start` 的取值范围是什么?`index + 1` 的最大下标是多少?会越界吗?
- `n = m` 时会发生什么?`n < m` 时呢?该不该加一条断言把这种情况拦在前面?(想想什么时候会真的撞上:在很小的 valid 集上、或者你为了 debug 把 `context_length` 调得很大时)

## 7. 建议的推进顺序

每一步都有**独立的验收信号**,不要跳步:

1. **下载数据**(A1)。`ls -lh` 确认大小。
2. **`from_files` + 序列化**(A2)。验收:存盘读回后 `encode` 结果逐个 id 相等。
3. **在 valid 集上跑通编码脚本**(A3 的小规模版)。验收:`decode(encode(全文))` 和原文一致;`max_id < vocab_size`。
4. **在 TinyStories train 集上训 BPE + 全量编码**(A2/A3 的完整版)。这一步耗时最长,挂后台跑,记下 token 总数。
5. **写 `train.py`,但先只跑 overfit 测试**:拿极小一段数据(比如几个 batch),看 loss 能不能压到接近 0。这是讲义 §7.2.3 点名的**最强 sanity check**,也是你笔记里的验收方法 ②。
6. **检查初始 loss ≈ $\ln(10000) \approx 9.21$**。这条最便宜、最灵敏,写完 forward 就能验,不用等训练。
7. **接上日志和验证集评估**(B-特别项 + D),跑一个短 run,确认曲线画得出来。
8. **中断恢复测试**:跑 200 步存档,杀掉,恢复,看接续处平不平滑(注意坑 ⑥)。
9. **正式训练**,冲 val loss ≤ 1.45(低资源档 ≤ 2.00)。
10. **写解码器**(C),生成 256 token 看看像不像人话。
11. **做 §7 的 ablation 实验**(D 里列的 7 项)。

第 5、6 步的顺序值得强调:**它们不需要 A 全部做完**。用 `tests/fixtures/tinystories_sample.txt` 加一个小 vocab 就能跑,先把 `train.py` 的骨架和顺序约束验对,再去等那个小时级的全量编码。这样即使编码脚本要重跑,你也不会连训练循环有没有 bug 都不知道。
