# memmap（内存映射）详解

背景：`train.py` 的 `load_tokens` 函数里用 `np.load(mmap_mode="r")` / `np.memmap` 打开 tokenize 好的数据文件。这里整理一下 memmap 这个概念本身，以及它在训练场景里为什么重要。

## 什么是内存映射（memory mapping）

内存映射是操作系统提供的一种机制：把一个**磁盘文件**直接映射到进程的**虚拟地址空间**里，让你可以像访问内存数组一样访问文件内容，而不需要显式调用 `read()` 把数据搬进内存。

对比"普通读文件"：

| | 普通读取（如 `np.load` 不加 mmap） | 内存映射（`mmap_mode="r"` / `np.memmap`） |
|---|---|---|
| 何时把数据搬进物理内存 | 调用时立刻整体搬入 | 只有真正访问某段数据时才搬入（懒加载） |
| 占用内存 | 等于文件大小 | 远小于文件大小，按需增长 |
| 打开大文件（远超内存）的可行性 | 可能直接 OOM | 可行，因为磁盘上的数据不需要全部驻留内存 |
| 底层机制 | 系统调用 `read()`，数据从磁盘拷贝到用户缓冲区 | 系统调用 `mmap()`，虚拟地址直接映射到文件，靠缺页中断按页加载 |

## 关键机制：缺页中断（page fault）触发的懒加载

1. `np.memmap(path, ...)` 调用之后，**几乎不产生任何磁盘 I/O**——它只是在虚拟地址空间里建立了一段"映射"，告诉操作系统"这段地址对应磁盘上的这个文件"。
2. 当你的代码第一次访问这段地址里的某个位置（比如 `data[1000:2000]`），CPU 发现这块虚拟地址还没有对应的物理内存页，触发**缺页中断**。
3. 操作系统这时候才真正从磁盘读取对应的那一页（通常是 4KB 对齐）数据，填进物理内存，然后让程序继续执行，仿佛这块内存"一直都在"。
4. 之后再次访问同一段数据，因为物理页已经加载过，直接命中内存缓存，不再触发磁盘 I/O（除非系统内存紧张，页面被换出）。

这整个过程对 Python/NumPy 层完全透明——你写的代码 `data[i:j]` 看起来和操作一个普通数组一模一样，底层是操作系统在悄悄按需搬运数据。

## 为什么训练场景特别需要它

`train.py` 里读取的是 tokenize 之后的整份语料（可能是几十 GB 甚至上百 GB 的 token id 序列），而训练时 `data_loader`（见 `tool.py`）每一步只是**随机采样一小段**（`batch_size × context_length` 个 token）：

```python
batch_start = np.random.randint(0, n - m, size=B)
index = batch_start[:, None] + np.arange(m)
inputs = torch.tensor(x[index], ...)
```

如果不用 memmap，`load_tokens` 一开始就要把整份语料**全部读进内存**——对于超大数据集这可能直接把机器内存撑爆，而且大部分数据在很长时间内根本用不上。用 memmap 之后：

- 数据**留在磁盘**，Python 进程里只保留一个"地址映射"，几乎不占内存。
- 每次 `data_loader` 随机切片时，只有**这一小段涉及到的磁盘页**才会被真正加载进内存。
- 多个训练进程/多次运行之间，操作系统的页缓存（page cache）还能复用同一份物理内存映射，不需要重复加载。

一句话：**memmap 让你可以"假装"整个超大文件都在内存里随便切片，而实际上只有用到的那一小部分才真正占用物理内存。**

## `np.load(mmap_mode="r")` 与 `np.memmap` 的关系

两者底层都是走 memmap 机制，区别只在于**文件格式是否自描述**（详见 [torch.cuda与torch.backends.mps用法整理.md](torch.cuda与torch.backends.mps用法整理.md) 之外的另一篇——这里单独说明）：

- **`np.load(path, mmap_mode="r")`**：用于 `.npy` 文件。因为 `.npy` 文件自带头部（记录了 dtype、shape），NumPy 能自动解析出这些信息，然后在头部之后的数据区做内存映射。你不需要手动传 dtype/shape。
- **`np.memmap(path, dtype=..., mode="r", shape=...)`**：用于没有头部的裸二进制文件（如 `.bin`）。因为文件不自描述，你必须手动告诉它 dtype（决定每个元素占几个字节、怎么解释字节），可选地传 shape（不传则默认为一维，长度按"文件字节数 ÷ dtype 字节数"推算）。

`mode` 参数控制映射的读写权限，常见取值：
- `"r"`：只读，不能修改（`train.py` 里用的就是这个，训练数据不应该被意外改动）。
- `"r+"`：读写，修改会直接写回磁盘文件。
- `"w+"`：新建或覆盖文件，可读写。
- `"c"`（copy-on-write）：可写，但修改只停留在内存里，不会写回磁盘文件。

## 一些容易忽略的边界情况

- **切片后的类型**：对 memmap 数组做切片（如 `data[100:200]`）返回的仍然是 `np.memmap` 对象（是原数组的一个视图），而不是普通的 `np.ndarray`；如果需要脱离内存映射、变成普通数组，需要显式 `np.array(data[100:200])` 做一次拷贝。这也是为什么 `data_loader` 里 `torch.tensor(x[index], ...)` 这一步会真正把数据从磁盘"物化"进 GPU/CPU 内存——`torch.tensor()` 会强制拷贝数据。
- **随机访问的性能**：memmap 对**顺序访问**特别友好（操作系统会做预读），但如果访问模式非常随机（正是 `data_loader` 里 `np.random.randint` 采样的场景），缺页中断会更频繁,如果数据存放在机械硬盘上会比较慢；不过在 SSD 上通常影响不大，这也是为什么训练脚本敢于用随机采样 + memmap 的组合。
- **值域自检为什么重要**：正是因为 memmap（尤其是 `np.memmap` 这种非自描述的路径）不会做任何数据校验，dtype 传错时它不会报错，只会把字节流错误地重新解释成看起来"合法"但语义上是垃圾的数字——这也是为什么 `load_tokens` 里专门加了一段值域自检（抽样检查 `min/max` 是否落在 `[0, vocab_size)` 内）。
