# Unicode 与编码基础知识整理(Tokenizer 相关)

## 1. 核心概念区分

- **字符(character)**:人类概念上的一个"文字单位"。
- **码位(code point)**:Unicode 标准给每个字符分配的编号,范围是 `U+0000` ~ `U+10FFFF`,是一个抽象的整数,不涉及具体存储方式。
- **字形(glyph)**:字体渲染出来的具体图形,同一个码位在不同字体下可能是不同的字形(甚至一个码位对应多个字形,或多个码位合成一个字形)。
- **编码(encoding)**:把码位序列转换成字节序列的具体方案,常见的有 UTF-8 / UTF-16 / UTF-32。

理解 tokenizer 时最容易混淆的就是"码位"和"字节"这两层,一定要在脑子里分清楚自己当前操作的对象是哪一层。

## 2. UTF-8 编码规则

- 变长编码,每个码位用 1~4 个字节表示。
- ASCII 范围(码位 0~127)编码后正好是单字节,且和传统 ASCII 编码完全一致,这是 UTF-8 被广泛采用的重要原因。
- 多字节序列里,首字节的高位 bit 模式标识了这个字符总共占几个字节,后续的每个字节都以 `10` 开头(称为 continuation byte)。
- 因为有这种模式,UTF-8 是"自同步"的:从任意一个字节位置往前找,总能找到一个字符的起始字节,不会因为丢了一个字节就导致后面全部错位(但截断/损坏仍然会导致这一个字符解析失败)。

## 3. Python 里 `str` 与 `bytes` 的区别

- `str` 存的是 Unicode **码位**序列,是一个抽象层面的对象,和具体编码无关。
- `bytes` 存的是某种编码方式**编码后**的字节序列,是具体、物理层面的对象。
- `str.encode(encoding)` → 得到 `bytes`;`bytes.decode(encoding)` → 得到 `str`。
- 常见错误:把 `bytes` 当 `str` 用,或者反过来。比如对一段 UTF-8 字节做 `len()`,得到的是字节数而不是字符数;如果字符串里有非 ASCII 字符,这两个数字通常不相等。

## 4. `encode` / `decode` 的 `errors` 参数

处理真实语料时经常会遇到非法或者被截断的字节序列,`errors` 参数决定了遇到这种情况时的行为,常见取值:

- `strict`(默认):遇到无法编码/解码的内容直接抛异常。
- `ignore`:直接丢弃无法处理的字节/字符。
- `replace`:用占位符(解码时通常是 `U+FFFD` 替换字符)代替。
- `backslashreplace` / `surrogateescape` 等:用于一些需要"无损保留"原始字节信息的场景。

在写 tokenizer 的训练/推理代码时,要想清楚自己到底希望在哪个环节用哪种 `errors` 策略,尤其是训练语料本身可能包含非法编码片段的情况。

## 5. 为什么 byte-level tokenizer 是对"字节"而不是"字符"做 BPE

- Unicode 码位空间有十几万个,如果直接对字符做 BPE,初始词表就非常大,而且还是可能遇到语料里没见过的新字符(OOV 问题)。
- 如果先把文本编码成字节,字节表只有 256 种可能取值,任何 Unicode 文本(不管什么语言、有没有 emoji)都能无损地表示成字节序列 —— 这样从根本上避免了 OOV。
- 代价是:一个人类意义上的"字符"(尤其是非 ASCII 字符)可能被编码成多个字节,BPE 的 merge 操作实际上是在学习字节层面的组合规律,而不是字符层面。

## 6. "字节 → 可打印 Unicode"的映射技巧(GPT-2 一脉常见做法)

- 直接拿原始字节值(0~255)当字符串处理会有麻烦:里面包含大量不可打印的控制字符、空白符,和很多基于字符串/正则的处理逻辑不兼容。
- 常见做法是把 256 个字节值**一一映射**到一批人类可读、可打印的 Unicode 码位上,这样字节序列就可以被当作普通字符串,跑基于字符的正则预分词、BPE 合并等逻辑。
- 注意这一步只是"表示层"的技巧,不改变字节本身携带的信息,是可逆的、一一对应的映射,不是有损压缩。
- 具体的映射规则建议自己参照课程讲义/论文推导一遍,理解"为什么这么设计"比记住映射表本身更重要。

## 7. 和 tokenizer 实现直接相关的常见坑点

- **预分词正则的作用层面**:如果预分词用的正则是基于 Unicode 字符属性(比如区分字母、数字、标点)做的,那这一步严格来说是在"码位"层面工作,和后续在"字节"层面做的 BPE merge 不是同一个粒度,顺序(先分词还是先编码成字节)需要想清楚。
- **不要混淆"字符 pair"和"字节 pair"**:BPE 训练时统计与合并的对象到底是什么粒度,决定了整个算法的正确性。
- **合并不能跨越预分词边界**:预分词把文本切成若干个片段(pre-token)之后,BPE 的合并操作通常只允许发生在同一个片段内部,不能跨片段合并 —— 这是很常见的 bug 来源,值得专门写测试验证。
- **特殊 token(special tokens)要单独处理**:不能让它们参与到普通文本的 BPE 切分逻辑中,否则可能被意外拆开成碎片。
- **非法/截断 UTF-8 序列的处理**:测试数据或者非英语语料中经常会出现,需要明确解码策略(参考第 4 节)。
- **surrogate pair 问题**:UTF-16 里的代理对本身不是合法的独立码位,如果数据处理链路中用到了类似 `surrogateescape` 之类的操作要格外小心边界情况。
- **Unicode 规范化(NFC / NFKC 等)**:同一个"看起来一样"的字符可能有多种不同的码位序列表示(比如带重音符号的字母,可以是一个组合码位,也可以是"字母+重音符号"两个码位拼出来的),是否需要规范化会影响 tokenizer 结果的一致性。课程作业通常不要求做规范化,但要清楚这是一个真实存在的问题。

## 8. 调试 / 验证建议

- 写一个最基本的 round-trip 测试:随机字符串 → encode → decode,结果应该和原始字符串完全一致。
- 针对非 ASCII 字符(重音字母、CJK、emoji 等)单独构造测试用例,确认多字节字符的边界没有在某个环节被意外切断。
- 遇到 decode 报错时,先定位是**哪个字节位置**出的问题,再回头看是预分词逻辑还是 merge 逻辑把一个多字节字符从中间切开了。
- 结合 profiler(比如之前提到的 `--durations` / `cProfile`)确认性能瓶颈到底在哪一层,避免凭直觉猜测。
