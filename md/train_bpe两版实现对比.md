# `train_bpe` 两版实现对比：old_bpe.py vs bpe.py

对比对象：

- `cs336_basics/old_bpe.py` 中的 `train_bpe`（第 56–116 行）
- `cs336_basics/bpe.py` 中的 `train_bpe`（第 55–139 行）

---

## 1. 一句话总结

两版的**第 1 步（初始化词表）和第 2 步（分块读取 + pre-tokenization）完全相同**，差别 100% 集中在**第 3 步的合并循环**上：

| | old_bpe.py | bpe.py |
|---|---|---|
| 策略 | **全量重算**（recompute from scratch） | **增量更新**（incremental update） |
| 每轮做什么 | 重新扫描整张 frequency 表统计 pair，再重写整张表 | 只统计一次 pair，之后靠增量修正；只重写受影响的词 |
| 辅助数据结构 | 无 | `pairs_to_frequency`（pair → 含该 pair 的词集合）倒排索引 |
| 需要维护的状态 | 只有 `frequency` | `frequency`、`pairs`、`pairs_to_frequency` 三者必须始终一致 |
| 正确性难度 | 低（每轮从零算，天然自洽） | 高（一致性维护是全部 bug 的来源） |

---

## 2. 完全相同的部分

以下内容两个文件逐字一致，不构成性能差异：

- GPT-2 的 `PAT` 正则、`find_chunk_boundaries` 的实现
- 步骤 1：`vocab` 初始化为 256 个单字节 + special tokens，`index` 记录下一个可用 id
- 步骤 2：按 `<|endoftext|>` 找分块边界 → 逐块解码 → 按 special tokens 切分 → `re.finditer(PAT, ...)` → 把每个 pretoken 拆成单字节 tuple 存进 `frequency` Counter

> 注：两版目前都是**串行**跑这 4 个 chunk 的（`num_processes = 4` 只用来切边界，没有真正起进程池）。这一点两边一样，所以不影响本文的对比结论，但它是两版共同的、尚未兑现的优化空间。

---

## 3. 核心差异：合并阶段

### 3.1 old_bpe.py 的做法（第 85–114 行）

`while` 循环体内部，每一轮都做两次**对整张 frequency 表的完整遍历**：

1. **第 86–92 行**：新建一个空 `pairs = Counter()`，遍历 `frequency` 中**每一个**词、每一个相邻位置，从零重新累加所有 pair 的计数。
2. **第 93–95 行**：`max` 选出最优 pair，写进 `vocab` 和 `merges`。
3. **第 97–113 行**：新建一个空 `temp = Counter()`，再次遍历 `frequency` 中**每一个**词，无论这个词含不含 `max_pair`，都走一遍内层 while 把它重写成一个新 tuple，塞进 `temp`。
4. **第 114 行**：`frequency = temp`，整张表被替换。

特点：每一轮结束后没有任何跨轮复用的状态。上一轮辛苦统计出来的 `pairs` 在下一轮开头被直接丢弃、从头再算一遍。

### 3.2 bpe.py 的做法（第 85–136 行）

1. **循环外（第 85–93 行）**：`pairs` 只在进入合并循环**之前统计一次**。同时建立倒排索引 `pairs_to_frequency`：每个 pair 映射到"包含它的词"的 **set**。
2. **每轮（第 96–99 行）**：`max` 选出最优 pair，写进 `vocab` 和 `merges`。
3. **每轮（第 101–134 行）**：只遍历 `pairs_to_frequency[max_pair]` 里的词——也就是**真正含有这个 pair 的那些词**，其余的词一律不碰。对每个受影响的词：
   - 第 111–116 行：在重写的同时，用 `+=` / `-=` 对 `pairs` 做**局部增量修正**（合并点左右两侧的旧 pair 减掉、新产生的两个 pair 加上）
   - 第 122–124 行：新词进 `frequency`，旧词出 `frequency`
   - 第 128–134 行：同步维护倒排索引——把旧词从它原有的所有 pair 的集合里摘掉，把新词登记进新词自己的所有 pair 的集合里

特点：跨轮复用 `pairs` 的统计结果，代价是必须手工保证三份数据结构在每一步之后仍然互相自洽。

## 4. 复杂度分析

记号：

| 符号 | 含义 |
|---|---|
| `W` | frequency 表里**去重后**的 pretoken（词）条数 |
| `L` | 每个词平均的 token 数 |
| `N = W × L` | frequency 表中 token 总量 |
| `M = vocab_size − 256 − |special_tokens|` | 合并轮数 |
| `P` | 当前不同 pair 的种类数（`P ≤ N`） |
| `S` | **单轮中受影响的词**的总长度（即含 `max_pair` 的那些词的长度之和） |

### old_bpe.py

| 步骤 | 每轮代价 |
|---|---|
| 重新统计 pairs（86–92） | `O(N)` |
| `max` 选取（93） | `O(P)` |
| 重写整张 frequency（97–113） | `O(N)`，外加 `W` 次 tuple 分配 + 1 次 Counter 分配 |
| **合计** | **`O(M × N)`** |

### bpe.py

| 步骤 | 代价 |
|---|---|
| 循环外统计一次（85–93） | `O(N)`，只做一次 |
| `max` 选取（98） | 每轮 `O(P)` |
| 更新受影响的词（101–134） | 每轮 `O(S)` |
| **合计** | **`O(N + M×P + Σ S)`** |

### 差在哪里

关键在 `S` 和 `N` 的差距。合并进行到中后期时，被选中的 pair 往往只出现在少数词里，`S` 通常比 `N` 小一到几个数量级。old 版本每轮无差别地把**所有** `W` 个词重建一遍（哪怕这个词跟 `max_pair` 毫无关系，第 98 行的循环也会为它构造一个全新的 tuple 和 Counter 条目），这部分纯属浪费——这就是主要的加速来源。

另外 old 版每轮 `O(N)` 的 pair 重统计也被彻底省掉了，换成了每轮 `O(S)` 的增量修正。

### 但 `M × P` 这一项没有改善

`max(pairs, key=...)`（第 98 行）仍然是**每轮对整个 pair 字典做一次线性扫描**，两版都是如此。当 `vocab_size` 变大（比如作业后面要求的 10k / 32k）时，这一项会逐渐变成新的瓶颈。

更值得注意的是：`pairs` 在 bpe.py 里**只增不减**。第 112 / 115 行的 `-=` 会把某些 pair 的计数减到 0，但**条目本身仍然留在 Counter 里**；而且 `Counter` 对不存在的 key 做 `-=` 会直接创建一个负数条目（`Counter.__missing__` 返回 0）。这意味着 `P` 会随轮数单调增长，`max` 每轮要扫的东西越来越多。

> 值得想一想的两个问题：
> 1. 这些计数为 0 或负数的僵尸条目，除了拖慢 `max`，有没有可能在某种边界情况下**被 `max` 真的选中**？什么时候会发生？
> 2. 如果要把 `max` 从 `O(P)` 降下来，需要一种什么性质的数据结构？它跟"计数会被增量修改"这个特点之间有什么矛盾？（提示：想想标准库里的堆不支持什么操作，以及"延迟删除 / 惰性校验"这个思路。）

## 5. 内存开销

| | old_bpe.py | bpe.py |
|---|---|---|
| 常驻 | `frequency`：`O(N)` | `frequency`：`O(N)` |
| 额外 | 每轮临时的 `temp` Counter：峰值再多一份 `O(N)`（旧表要等 114 行换掉后才能回收） | `pairs_to_frequency` 倒排索引：`O(N)`（每个 token 位置贡献一条 pair→word 记录）；`pairs` 因僵尸条目持续膨胀 |

两版峰值内存量级相当，但 bpe.py 的额外开销是**常驻**的、且会随僵尸条目缓慢增长；old 版的额外开销是每轮一过性的。

---

## 6. 正确性代价：为什么增量版这么难写对

old 版的合并循环是**无状态**的：每轮开头 `pairs` 从零重建，所以它永远不可能跟 `frequency` 脱节。代价是慢，好处是几乎不可能写错。

bpe.py 引入跨轮复用的状态后，必须同时保证三条不变量成立。调试过程中遇到的每一个报错，本质上都是其中某一条被破坏了：

| 曾出现的症状 | 被破坏的不变量 |
|---|---|
| `KeyError: (b' ', b't', b'h', b'e')` | 倒排索引里残留了已从 `frequency` 中删除的旧词 |
| 遍历中修改 set 报错 | 外层正在遍历 `pairs_to_frequency[max_pair]`，内层又在增删同一个 set |
| `list.pop(tuple)` 类型错误 | —（API 误用） |
| merges 顺序 / vocab 内容与参考实现不符 | `pairs` 的计数与 `pairs_to_frequency` 的索引内容不同步 |

这是一个很典型的工程权衡：**用"手工维护的冗余索引"换性能，换来的复杂度全部体现在一致性维护上**。

## 7. 建议加上的不变量检查

与其在大语料上肉眼 debug，不如把上面那三条不变量写成断言，在 `while` 循环末尾（第 136 行前后）临时打开，用小语料跑一遍。三条候选：

1. **索引不含幽灵词**：`pairs_to_frequency` 所有集合里出现的每一个词，都必须仍然是 `frequency` 的 key。
2. **索引不漏词**：对任意 pair `p`，`frequency` 中所有真正含有 `p` 的词，都必须出现在 `pairs_to_frequency[p]` 里。（这条和上一条合起来就是"索引 ⟺ 事实"。）
3. **计数与事实一致**：对任意 pair `p`，`pairs[p]` 必须等于"遍历当前 `frequency`、按 old_bpe.py 第 86–92 行那种全量方式重新数一遍"得到的结果。

第 3 条尤其有用——它等价于拿 old 版当**参考实现**来交叉验证增量版。既然 old_bpe.py 就在手边，最直接的回归测试是：**同一份小语料、同样的 `vocab_size`，两版跑出来的 `merges` 列表应当逐项相等**。这比对着 pytest 的 snapshot 报错猜要快得多，而且能精确定位到**第几轮**开始分叉。

## 8. 当前 bpe.py 里还值得再看两眼的地方

不是结论，是几个可以自己核对的疑点：

- **第 133 行**：`for new in new_pairs:` 循环体内出现了 `pairs_to_frequency[old].discard(key)`，但这里的 `old` 是上一个 for 循环（第 130 行）结束后残留的变量值，跟当前的 `new` 无关。想一下这行到底想做什么、是不是第 131 行的重复，以及它的存在会不会误导后面读代码的人。
- **第 125–126 行的 `len(new_key) == 1` 分支**：这时直接 `pass`，跳过了整段索引维护。但这个词原本是长度为 2、含有 `max_pair` 的词，它在 `pairs_to_frequency[max_pair]` 里的那条记录有没有被清理掉？如果没有，它会在什么条件下变成"幽灵词"？（可以用上面第 1 条不变量直接测出来。）
- **重叠 pair 的场景**：像 `"aaa"` 这样 `max_pair = (a, a)` 且两次出现相互重叠的输入，第 111–116 行的左右邻居增减是否会重复扣减同一个 pair？建议单独构造这个最小样例跑一遍，对照手算结果。

---

## 9. 结论

- **性能**：bpe.py 的核心优化是"**只重算受影响的部分**"——省掉了 old 版每轮两次的全表 `O(N)` 扫描，把每轮成本从 `O(N)` 压到 `O(S + P)`。在 `S ≪ N` 的典型情况下这是数量级的提升。
- **仍存在的瓶颈**：每轮 `O(P)` 的 `max` 线性扫描没有改善，且 `pairs` 中的僵尸条目会让 `P` 持续膨胀。这会在 `vocab_size` 增大时暴露出来。
- **代价**：从"无状态重算"变成"有状态增量"，正确性负担全部转移到了三份数据结构的一致性维护上。保留 old_bpe.py 作为参考实现来做交叉验证，是当前性价比最高的调试手段。
